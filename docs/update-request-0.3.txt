# 1. ADD PIXEL SIZE

The add-on already calculates pixel density.

Add **Pixel Size** as a separate calculated value.

Definitions:

Pixel Density:
`pixels per metre`

Pixel Size:
`physical size of one projected pixel`

Calculate nominal pixel size from projected image width:

`Pixel Size = Image Width / Resolution X`

Display Pixel Size in:

`mm/px`

Example:

Image Width = 10 m  
Resolution X = 3840

Pixel Size ≈ 2.60 mm/px

Show both:

- Pixel Density: px/m
- Pixel Size: mm/px

Keep the calculation modular so later we can support separate horizontal and vertical pixel size if projection distortion is analysed.

# 11. TRUE PROJECTOR BEHAVIOUR

The current projection behaviour needs to be changed so the system behaves like a real projector.

The most important distinction is:

**Target = centre-ray reference for calculations**

**Projection receivers = any scene geometry intersecting the projector frustum**

These must be treated as separate concepts.

---

## AUTOMATIC PROJECTOR TARGET

Do not require the user to manually assign a target object during normal operation.

The projector's current target should be determined automatically.

Definition:

Cast a ray from the projector lens through the exact centre of the projector raster.

The **first scene geometry hit by that centre ray** becomes the projector's current target.

Automatically determine and store:

- Target Object
- Target Point
- Target X/Y/Z
- Target Distance

Recalculate this whenever:

- the projector moves
- the projector rotates
- relevant scene geometry moves

If the centre ray does not hit any geometry:

- show `No Target`
- do not show misleading calculated target values
- the visible projector beam/frustum should still exist

The target is a calculation reference only.

It must not define where the projected image stops.

---

## PROJECTION RECEIVERS

Any scene geometry that enters the projector raster/frustum should immediately receive the projected image.

Receiving projection must **not** require:

- being the centre-ray target
- being manually assigned
- being selected
- being tagged as a screen
- being the first object hit by the centre ray

If an object enters any part of the projection frustum, the appropriate portion of the projected raster should appear on it.

This should update in realtime while objects or projectors are moved.

---

## MULTI-SURFACE PROJECTION

The projector must behave as one continuous perspective image projected through space.

Different parts of the raster may hit different objects at different distances.

Example:

- centre of raster hits a screen at 10 m
- left edge misses the screen
- left edge continues travelling
- left edge hits a wall at 15 m

Expected result:

- the screen receives the centre portion of the image
- the wall receives the correct left portion of the same projected image
- projection does not terminate globally at 10 m

Another example:

A small object moves into the lower-right corner of the projector raster.

Expected result:

- that object immediately receives the lower-right portion of the projected image
- the object does not become the projector target unless it crosses the centre ray

---

## OCCLUSION

Projection should respect physical line-of-sight behaviour.

Each projection ray should effectively behave independently.

If foreground geometry blocks a particular part of the raster:

- that foreground geometry receives that part of the image
- geometry directly behind it should not receive the same ray

However:

- rays passing beside the foreground object must continue
- those rays may hit geometry farther away

Do not treat one object intersection as a hard clipping distance for the whole projector.

---

## NO TARGET-BASED CLIPPING

The current implementation appears to stop the projected output at or near the target plane.

Remove this behaviour.

The centre target must never act as:

- a clipping plane
- a maximum projection distance
- a projection surface boundary
- a visibility mask for other receiving geometry

The projector frustum should continue beyond the centre target.

The only thing that should stop a particular projected ray is:

- geometry intersecting that ray
- an explicit configurable far-range limit if one is added later

---

## CONTINUOUS IMAGE COORDINATES

Projected image coordinates must remain consistent across all receiving geometry.

The same virtual projector raster should be used everywhere.

Do not restart, stretch or independently fit the image per object.

For example, if PJ01 displays a calibration grid:

- the grid must remain spatially continuous across multiple pieces of geometry
- cell positions should correspond to the same projector pixel coordinates
- moving geometry through the frustum should reveal the appropriate portion of the same grid

This applies to:

- Solid Colour
- Calibration Grid
- Identifier
- Checkerboard
- Blender UV Grid
- Custom Image

---

## TARGET-BASED CALCULATIONS

Continue using the automatically detected centre-ray target for primary study calculations.

Use the centre target distance as the nominal throw distance.

From this calculate:

- Throw Distance
- Image Width
- Image Height
- Pixel Density
- Pixel Size
- DPI
- Estimated Illuminance

These are nominal centre-target calculations.

The actual visible projection may span geometry closer to or farther from the centre target.

Make this distinction clear in the code architecture.

---

## REALTIME REQUIREMENT

This behaviour must update interactively.

When:

- a projector moves
- a projector rotates
- an object moves into the beam
- an object moves out of the beam
- an object crosses the centre ray

the visible projected result and centre target should update immediately or close to realtime.

Do not require a manual refresh.

---

## IMPLEMENTATION GUIDANCE

Do not solve this by brute-force Python raycasting every projector pixel.

The engineering calculations and the visible projection should remain separate systems.

Recommended architecture:

### Engineering Layer

Use lightweight raycasting for:

- centre target
- target distance
- calculation values

### Visual Projection Layer

Use an efficient Blender viewport/GPU/projective-texture approach capable of:

- perspective projection
- multiple receiving objects
- depth-aware visibility
- realtime movement
- continuous raster coordinates

EEVEE / GPU-based techniques are preferred if practical.

Do not make Cycles mandatory for normal study work.

The visual projection system must not depend on manually identifying a target object.

# 12. PROJECTION ENGINE ACCEPTANCE TEST

Create a simple test scene containing:

- PJ01
- a small foreground plane
- a larger wall several metres behind it

Aim PJ01 so the centre ray hits the foreground plane but the foreground plane covers only part of the raster.

Expected behaviour:

1. PJ01 target becomes the foreground plane.
2. Centre target distance reports the distance to the foreground plane.
3. The foreground plane receives the corresponding centre area of the projected grid.
4. Parts of the raster extending beyond the foreground plane continue onto the wall behind.
5. The wall receives the correct remaining portions of the same grid.
6. The foreground plane casts a projection shadow onto the wall where it blocks PJ01.
7. Moving the foreground plane sideways updates the projection in realtime.
8. Once the foreground plane no longer crosses the centre ray, PJ01's target automatically becomes whatever the centre ray hits next.
9. No manual target assignment is required at any point.
10. Switching PJ01 to Blender UV Grid preserves exactly the same geometry, occlusion and multi-surface behaviour.

This behaviour is a hard requirement for the projection engine.
